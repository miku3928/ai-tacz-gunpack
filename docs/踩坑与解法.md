# 把事故变成知识

这份文档不写「项目在哪、命令怎么跑」。它写的是**我在这个系统上撞过的墙，以及撞完之后
能带走的东西**——抽象成模式，而不是记成事件。

每个模式给四件事：**长什么样（识别信号）／为什么会这样（机制）／怎么处理／代价是什么**。
事件只在需要当证据时出现，而且带上当时的数字，因为「感觉偏了一点」这种记录没有用。

---

# 第一部分：先理解这类系统的本质

## P1 · 沉默系统

**识别信号**：东西不对，但日志干净，游戏照常跑。

TaCZ 的加载路径几乎全部长这样：拿不到 → 跳过。这不是偷懒，是合理的工程取舍——
枪包是玩家自己装的第三方内容，一个坏包不该让游戏崩。代价是**所有错误都从"异常"
降解成"没有效果"**。

它带来三个必须记住的推论：

1. **错误会从字段级升级到文件级。** 一个字段的反序列化失败，整份数据的注册就被放弃。
   我遇到的形态：`extended_mag_ammo_amount` 写成 1 项（要求 3 项），Gson 抛异常，
   **整把枪从索引里消失**，物品退化成紫黑格 + 原始翻译键。
   看起来像"贴图丢了"，实际是"这把枪不存在了"。

2. **"看起来差不多"与"完全没生效"在视觉上不可区分。** 我改了三版渲染参数，
   三张输出图字节完全相同（同 sha256）——参数根本没走到渲染路径上。

3. **你必须自带裁判。** 系统不会告诉你对不对，所以"我觉得对"是唯一可得的信号，
   而它是不可靠的。

**怎么处理**：建立判据的等级，永远用能做到的最高一级。

| 等级 | 判据 | 可靠性 |
|---|---|---|
| 1 | 日志里的一行（加载失败、异常名、被忽略的字段） | 最高 |
| 2 | 数值（距离、角度、索引、文件 md5） | 高 |
| 3 | 结构化图（分帧对照、曲线、直方图） | 中 |
| 4 | "我看了一眼成品图，感觉对" | 基本为零 |

我绝大多数弯路都是因为拿第 4 级当第 1 级用。

---

## P2 · 数据驱动的引擎把名字当 API

**识别信号**：某根骨、某个类型、某个 tag、某个文件名，写错不会报错，只是"没反应"。

这类引擎里，**名字就是接口**，而且有四种完全不同的"名字"在同时起作用，很容易搞混：

- **对象名**（骨骼名）：决定谁挂谁下面、谁的变换被谁继承。
- **系统保留名**：被代码按名字接管，行为由代码写死。TaCZ 里
  `sight` / `sight_folded` / `mount` / `mag_standard` / `mag_extended_N` /
  `muzzle_flash` / `bullet_in_*` / `shell` / `righthand_pos` / `lefthand_pos` 都是。
- **分类名**（tag 名）：只是候选集的分组，**不等于**类型。
- **类型名**（枚举）：只有固定几个合法值。

踩过的三个具体形态：

1. 我把自带瞄具挂在 `scope_default`——这个名字**没有被任何代码接管**，所以它永远可见。
   装上新瞄具之后两个镜叠在一起。改挂 `sight` 才被 `isEmpty(scope)` 接管。
2. 我以为 `bayonet` 是一种附件类型。实际上类型枚举只有七个
   （`scope / muzzle / stock / grip / laser / extended_mag / NONE`），
   官方的 `bayonet_m9` 索引里写的是 `"type": "muzzle"`，
   bayonet 只是一个 tag 名。
3. 我以为 tag 名必须等于类型名。官方几十个 tag 名
   （`scope_sight` / `grip_vertical` / `pistol_muzzle` / `light_extended_mag` …）
   全都收敛到那七个类型。

**为什么容易错**：这四种名字在 JSON 里长得一模一样，都是字符串。分不清就会对着
一个字符串做错判断。

**怎么处理**：在给任何东西命名/挂名之前，先问**「这个名字有没有被代码接管」**。
答案只有三种：被接管（行为由代码定）、是分类（只影响候选集）、无人认领（永远可见）。
没有第四种。

---

## P3 · 语义先于数值

决定动画对不对的，往往不是数字，而是三个语义选择：

| 语义 | 选错的表现 | 这个系统的答案 |
|---|---|---|
| **替换 vs 叠加** | 整段姿态翻倍 | `shoot` 是叠加（`runAnimation("shoot", track, true, ...)`） |
| **父子 vs 兄弟** | A 动 B 不动，永远分离 | 官方把弹匣挂在手骨下面（同子树） |
| **绝对 vs 增量** | 静止时一切正常，一动就错 | position 通道是增量，且单位是 model unit |

第三条最阴险：**静止时 offset = 0**，所以任何静态验证都是对的。单位之争拉锯了很久，
因为双方都能自洽地解释所有不动的画面。

**怎么处理**：先回答语义问题，再调数值。数值错只错一点，语义错整段崩。

# 第二部分：判据论（这一路最贵的一课）

## P4 · 判据必须在真实语料上标定

**识别信号**：你有一个判据，但它说"有问题"，而你觉得东西其实还行。

我写了一个离屏第一人称渲染器复刻游戏的投影链。数学上对，但**相机比游戏近**。
倾斜到峰值时机匣跑到画布外，看起来像严重穿帮。我为此花了很久调"拉远"，效果都一般。

转折点：拿同一套投影去渲**官方 50 把有换弹动画的枪**，量它们的屏幕包围盒：

```
官方换弹全程峰值中位:  nx 0.02..1.02   ny -3.19..-0.05
个体差异极大:          m4a1  nx -3.80..7.23    m16a4 nx -10.75
                       spr15hb nx -139          uzi  nx +104
```

**官方自己也大量出框，而且比我夸张得多。** 所以"出框"根本不是穿帮的判据——
它是我这套渲染器的产物。

**元判据**：任何判据在信任之前，先拿 ground truth 跑一遍分布。
**官方也会"失败"的判据是无效判据。**

这条不只对渲染成立。校验器规则、几何比例、数值合理性，全都适用。

---

## P5 · 证据的形状

同一条经验的三种写法，价值差三个数量级：

- ❌「手的位置调好了」——不可验证，也不可迁移。
- ⚠️「手的世界坐标和弹匣重合」——可验证，但只覆盖一个时刻。
- ✅「换弹全程，手套质心与弹匣质心的**世界距离**与**屏幕像素距离**，在手应当抓握的
  时间段内均为 0.00；提匣段 25.6 px（弹匣此时隐藏）；首尾 65 px（手已回到护木）」
  ——可验证、可回归、可迁移，而且**它自己就说明了什么算对**。

好判据有三个特征：
1. **能给出数字**，不是形容词。
2. **有对照**（0 和 65 的对比说明了两端分别在做什么）。
3. **不依赖观察者**（换个人跑同样的脚本得到同样的数）。

我踩过的反面例子：我用分帧图"看"出弹匣被抓住了，实际算出来差 4 个单位；
而那三张图 md5 完全一样，说明我改的那次根本没生效。**图和"我改了"都不是证据。**
md5 和数值才是。

---

## P6 · 两个都自洽时，去找那个唯一的系数

**识别信号**：两个解释都能解释现有全部证据，你开始反复推演"如果 A 则……如果 B 则……"。

position 通道的单位之争就是这种局面。归一化（block↔model unit 的 1/16）**只可能发生在
一处**，读到它比赛推理快得多：

```
Animations.writeBedrockTranslation: 每个 Vector3f 关键帧 mul(0.0625, 0.0625, 0.0625)
BedrockPart.translateAndRotateAndScale: translate(offset) 不再除 16；只有 pivot 除 16
```

结论：1 个 JSON position 单位 = 1 model unit。两套 FK 我写了又比、比了又改，
真正定论只花了一次反汇编。

**推广**：一个系统里，单位换算、坐标系变换、缩放系数，这类"全局常量"通常只有
一个权威位置。找到它，不要用行为反推。

# 第三部分：可迁移的取证方法

## P7 · 定位问题的四级台阶（成本递增，顺序不能颠倒）

1. **读日志**：有没有异常、有没有"被忽略"。成本最低，信息最高。我最大的两个坑都是
   日志里明写的，我只是先入为主地没去看。
2. **二分资源**：文件在不在、路径拼对没有、命名空间对不对。**跨包引用**要在这一步
   想清楚——一个包指向另一个包的资源是合法的，别当缺失。
3. **比数据形状**：拿官方同名字段逐个比类型、数组长度、嵌套键。这一步抓到了
   上面那个"整把枪消失"。
4. **看几何/动画**：最贵，也最少是真凶。

跳过前三级直接看几何，是我浪费时间的标准姿势。

---

## P8 · 用射线代替眼睛定位几何问题

**识别信号**：模型上"应该"有个洞/凹槽，但渲染出来是平的。

这次做对的一套动作，值得复用：

1. **排除渲染器**：正常渲一张，再**删掉可疑零件**渲同一机位，比 **sha256**。
   完全相同 → 那个零件被完全遮住。这是"被挡住"的硬信号，不是审美判断。
2. **排除布尔没生效**：统计目标矩形内的三角面数与所在平面坐标。外壁确实没了 → 布尔切了。
3. **一击定位**：对场景里每个对象做 `ray_cast`，从可疑方向打过去，
   列出该区域内**每一个**命中面的坐标与所属对象。

结果一眼看到真相：窗口里堵着**装饰板的三层内壳**（y = −24.6 / −23.6 / −22.9），
而真正的槽底在 y = −8.0。原因是那块装饰板由几层重叠壳体 union 而成，
EXACT 布尔只切掉了最外层。

**推广**：几何问题先问"**这个位置到底有什么**"，再决定改什么。调相机、重渲、加光
都是在猜。

---

## P9 · 读实现，不读文档

**识别信号**：文档说 A，行为像 B；或者根本没有文档。

这个系统没有格式文档。作者也没有混淆——方法名全是可读的，只是没写下来。
所以「读实现」的成本比想象中低。

**什么时候值得读**：只有当两个解释都自洽、且**用现有证据无法区分**时。
平时优先用"官方成品当参照物"（见 P10），便宜两个数量级。

**几个实操**：
- **别读方法名，读被调用的常量。** Forge 会把方法名重映射成 `m_252880_` 这种占位符。
- **日志文案可能是错的。** 它打印 `Registered model type: meshy`，而注册的字符串键
  其实是 `mesh`（作者手滑多打了个 y）。文档、注释、日志都会骗你，常量池不会。
- **归一化系数常以位模式出现。** `ldc_w 1031798784` 就是 float 0.0625。看到大整数先转浮点。
- **lambda 走 invokedynamic**，操作数指向 BootstrapMethods 表，要先解析那张表才能
  追到具体方法体。

三次关键定论都来自这里：单位（0.0625）、哪些零件被自动隐藏（构造器里逐个
`setFunctionalRenderer`）、附件可装性（`List.contains(AttachmentType)`）。

---

## P10 · 用别人的成品当规范语料

**识别信号**：你要决定一个比例、一个偏移、一个结构、一个枚举值，但没有规格说明。

官方 55 把枪 + 一堆第三方包，就是一份免费的、已经被引擎验证过的语料。
**统计，不要猜。**

这一路靠统计解决的问题：

| 问题 | 统计量 | 得出的规则 |
|---|---|---|
| 瞄具黑边多厚算正常 | 环外径 / 目镜半径 | 官方 1.01–1.13，我原来 2.05 |
| 手该放在哪 | 手方块中心 − 握把几何中心 | 中位偏移 + 一个标准差范围 |
| 弹匣该挂在谁下面 | 骨骼树父子关系 | 官方挂在手骨下（同子树） |
| 改装界面朝向 | 496 个 geo 的 refit 骨 rotation | 中位 `[0,90,0]` |
| 有多少种附件类型 | 全包索引枚举值计数 | 只有 7 种，bayonet 不是其中之一 |
| 手姿态该写在哪个 clip | 官方动画通道集合 | 写在 static_idle，shoot 里不写 |

**代价**：统计量只给你分布，不给你意图。落在分布里不等于好看——所以比例类问题
统计完还是要人看一眼，而结构类问题（谁挂谁下面）统计完可以直接用。

# 第四部分：决策模式

## P11 · 结构问题不能用数值长期修补

**识别信号**：你在给 A 写"跟着 B 走"的通道，而不是让 A 成为 B 的子级。

我的弹匣和手在树上是**兄弟**，官方是**父子**。改树会波及所有已有动画和支点，
所以我选了数值解：给手补一个位移通道，让它跟着弹匣。

这是可行的，但它有三笔代价，都必须付：
1. 偏移必须在**动画姿态**下求解。我第一次在静止姿态下算，差了 3.9 个单位——
   因为每个动画都把手转到很远的地方去了。
2. 必须知道通道到世界坐标的映射（含 Y 轴取反）。
3. 必须用不依赖眼睛的判据验证（世界距离 + 屏幕距离）。

**结论不是"永远改结构"，而是**：数值补丁是可接受的工程选择，但要清楚它是补丁，
并且它的验证成本比改结构高。如果这个约束还要重复三次以上，就该改结构。

---

## P12 · 布尔不是万能开孔工具

**识别信号**：布尔"切了"，但视觉没变。

布尔适合"整块零件相交"，不适合"在多层重叠壳上挖窗口"。多层 union 之后，
EXACT 求解器只切得到最外层。

替代方案更可控：**bmesh 按重心筛面 → 删面**。而且要顺手把被观察的零件往后退一点
（我把枪机外表面退了 6 mm），让窗口里看到"凹进去的一条"，而不是"堵在洞口的板子"。

---

## P13 · 规则写窄了比没规则更危险

**识别信号**：你的检查器在一个广泛使用的成品上报出成百上千条问题。

我把自己的踩坑经验固化成校验规则，跑在官方包上：**1281 个 error**。
那不是官方包的问题，是我把"我见过的写法"当成了"唯一正确的写法"。

逐条被官方反证的记录（这才是有价值的部分）：

| 我以为是规则 | 官方反证 | 真实语义 |
|---|---|---|
| 每个动画都必须有手通道 | 108 + 86 条违反 | 手写在 static_idle，shoot 里不写 |
| tag 名 == 类型 | 几十个 tag 名 | tag 名自由命名，映射到 7 个枚举 |
| tag 的类型必须在 allow 列表里 | 100+ 处 | 可装性只看 allow 列表，tag 只筛候选 |
| 附件 geo 必须单骨 | 9 骨、13 骨 | 整个模型可以画在挂点上 |
| 瞄具必须有 scope_body 几何 | 全是方块，几何在子骨 | 只要求子树有几何 |
| 弹壳必须有模型和贴图 | 官方 5 个键，无模型 | 弹壳几何在弹药 display 里 |
| 通道值必须是三元数组 | 7 处 `"scale": 0` | 标量 = 三轴同值 |
| 换弹时间要短于冷却 | 霰弹枪故意反过来 | 逐发装填时冷却是**每发**间隔 |
| bayonet 是一种类型 | 索引写 `type: "muzzle"` | 类型只有 7 个 |
| 关键帧不能超过片段长度 | 一堆 `0.4667 > 0.4667` | 浮点末位误差，不是越界 |

从 1281 降到 **1**，而剩下那条是真的（官方一个 tag 指向了不存在的附件）。

**两条元判据**：
- 一条规则在官方包上命中成百上千次 → **规则错**。
- 一条规则在任何包上都不命中 → 它可能**没在检查真东西**，只是把习惯写成了规矩。

**代价**：放宽规则会漏掉真问题。所以每次放宽都必须能说出"官方为什么这样也是对的"，
说不出来就不许放宽。

---

## P14 · 连续的、主观的东西交给人；离散的、可判定的交给机器

用户说过一句话点醒我：「你的识图能力完成这个任务有点困难」。

第一人称位置是连续的、主观的、需要即时反馈的。我去截图、猜、再截图，收敛极慢。
正确做法是**做工具给人**：滑杆、拖动画布、滚轮远近、把游戏内截图当半透明底图对齐、
改完就地写回包。

于是分工清晰了：
- **离散可判定**（路径对不对、骨骼名连没连、绕序反没反）→ 校验器，机器判。
- **连续主观**（位置好不好看）→ 工具，人判。
- **我的边界**：我能读结构化图形（分帧、曲线、直方图），读不出"这个位置舒不舒服"。

**最关键的细节**：工具必须能**载入游戏内截图做对齐底图**。这一步把"我的坐标系"
和"游戏"接上了，否则工具再顺手也只是在自洽。

# 第五部分：记录方法本身

这一路我写过好几版笔记，只有最后这版是能用的。差别在**每条记什么**：

```
症状      ：别人也能认出来的现象（不是"感觉偏了"，是"开火时手臂折叠"）
我以为是  ：当时最自然的错误解释（这是最有价值的一行——下一个人会和你一样想）
其实是    ：机制层面的真因
判据      ：怎么才算证明了"其实是"（数字、日志行、差分图）
代价      ：这个解法换来了什么新义务（要重新验证什么、会引入什么耦合）
```

「我以为是」这一行是这份文档真正的价值。**只写正确答案的笔记，下一个人会重新走一遍
你的错误解释。**

还有一类必须写：**已知的未知**。哪些结论有代码但没经过最终裁判（游戏），
哪些是统计推出来的而不是验证过的。不写这个，下一个人会把"推测"当"已验证"，
然后在上面盖第二层。
